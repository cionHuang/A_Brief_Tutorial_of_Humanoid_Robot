## 先看一个现场问题

设想这样的调试场景：机器人在仿真里能稳定抬起前臂，但在控制真机时，却偶尔晚一点才会响应。程序没有崩溃，通信也没有断开。查看记录才发现：控制程序本该开始计算时，处理器还在忙着记录日志。

你也许会问：

> “程序一直在运行，为什么控制命令还会迟到？说好的 2 ms 控制周期，究竟要怎样才能保证？”

上一节讲了数据怎样及时送达。这一节接着看：数据到了以后，软件怎样安排采样、计算和输出，让一次控制更新按时完成。

运行在控制板、驱动器等设备中，负责控制硬件的软件，称为嵌入式软件（Embedded Software）。其中，实时系统（Real-time System）既要求结果正确，也要求结果在规定的截止时间（Deadline）前产生。

## 计算平台各自负责什么

机器人里的计算工作各有要求。规划动作、处理图像需要较强的算力；采集电流、更新电机输出则需要紧密配合硬件时序。常见的计算平台可以这样认识：

| 名称 | 是什么及常见用途 |
| --- | --- |
| MCU（Microcontroller Unit，微控制器） | 把处理器、存储器和多种硬件接口集成在一颗芯片中，常用于传感器采样、电机控制和保护逻辑 |
| DSP（Digital Signal Processor，数字信号处理器） | 擅长反复进行乘加等运算，常用于滤波、信号处理和电机控制；一些 MCU 也具备这类运算能力 |
| SoC（System on Chip，片上系统） | 在一颗芯片中集成处理器、存储控制器和多种接口；机器人中常见的 SoC 计算模块可运行 Linux、处理图像或运行中间件 |
| 工控机（Industrial PC，IPC） | 一类面向工业应用的计算机，常承担感知、规划、日志和模型推理等工作，也可配合 GPU 加速计算 |

MCU、DSP、SoC 是芯片层面的名称，功能也可能重叠；工控机则是一台计算设备。实际分工还要看硬件接口、计算负载，以及操作系统和软件怎样安排任务。

> **一句话听懂**：不同平台适合承担不同工作；计算能力强，不等于每次都能按时完成。是否满足实时要求，要看硬件和软件的配合。

## MCU 如何连接真实硬件

### GPIO、ADC、PWM 与定时器

**GPIO（通用输入输出）**用于读取或输出高、低电平。例如，读取开关状态，或控制驱动器的使能信号。

**ADC（模数转换器）**把模拟电压转换为数字。配合采样电路，控制器就能读取电流、电压、温度等信息。

**PWM（脉宽调制）**用占空比规定开关在一个周期内导通多久。电机驱动器通过它调节绕组电压，进而影响电流，具体原理见 [3.2 节](./02-motors-drivers-servo-control.mdx)。

**定时器（Timer）**提供时间基准，可以产生周期信号、触发采样或记录脉冲到达的时刻。在电机控制中，它还可以协调 PWM 与 ADC，让电流在选定的时刻被采样，再由控制程序根据读数更新输出。[3]

> **一句话听懂**：GPIO 读写开关信号，ADC 获取采样值，PWM 控制开关的导通时间，定时器协调这些动作的时刻。

### DMA、中断与缓冲

传感器不断产生数据，程序不一定能立刻处理，通常需要先把数据放在内存中的一块区域里，这就是缓冲区（Buffer）。直接存储器访问（Direct Memory Access，DMA）可以把数据从外设搬到内存，减少处理器逐个搬运数据的工作。

一批采样完成或通信数据到达时，硬件可以通过中断（Interrupt）通知处理器。处理器转去执行中断服务函数（ISR），处理这个事件。这里的工作应尽量简短；如果忙着打印日志或进行复杂计算，就可能推迟其他需要及时处理的工作。[3]

数据存好了，还要避免程序读到一半更新、一半未更新的内容。一种常见办法是双缓冲：先在一块缓冲区中写入新数据，写完后再交给程序读取，下一批数据改写另一块；交换时要保证写入已经完成、读取仍在使用的数据不会被覆盖。至于数据是否过期，仍按上一节介绍的时间戳和序列号来判断。

> **一句话听懂**：DMA 负责搬运数据，中断通知程序处理事件，缓冲区暂存数据；程序要读到一份完整、可用的数据。

## 裸机与 RTOS

### 裸机循环（Bare-metal Superloop）

裸机系统不运行操作系统。完成必要的初始化后，一种常见写法是在 `while(1)` 主循环中，依次读取采样、计算控制量、更新输出、处理其他工作，再回到开头。

这种写法简单，容易看清执行顺序。但如果记录日志的函数突然变慢，下一轮采样和控制也会跟着推迟。裸机程序也可以使用定时器和中断；能否按时完成，仍取决于各项工作怎样安排。

> **一句话听懂**：主循环按顺序做事，一步耗时变长，就会让后面的工作等待。

> 读取采样 → 计算控制量 → 更新输出 → 处理其他工作 → 返回开头

### RTOS、任务与优先级

工作变多后，可以把控制、通信、日志等工作划分成不同的任务，交给实时操作系统（Real-time Operating System，RTOS）调度。任务是可以被独立安排运行的一段程序；优先级用来规定任务之间的先后次序。[4]

以常见的单核抢占式调度为例：日志任务正在运行时，控制任务被唤醒。如果控制任务的优先级更高、也已具备运行条件，系统就会暂停日志任务，先运行控制任务。[4]

这样，控制工作就不必总等主循环绕完一圈。具体谁先运行，要按任务的时限和故障后果安排；使用 RTOS 之后，也仍需限制每个任务占用处理器的时间。

> **一句话听懂**：RTOS 按规则安排任务，让需要及时处理的工作优先运行；任务怎样划分、优先级怎样设置，仍要由开发者设计。

### 优先级反转

优先级高的任务，也可能被低优先级任务挡住。比如，日志任务正在访问一份共享数据，并持有互斥锁（Mutex）；这把锁用来保证同一时刻只有一个任务访问它。控制任务也要用这份数据，就只能等日志任务释放锁。

如果此时还有一个中等优先级的任务不断抢占处理器，日志任务就更难运行并释放锁，最高优先级的控制任务反而一直等待。这就是一种典型的优先级反转（Priority Inversion）。[2][4]

设计时应尽量减少控制任务对这类共享资源的等待。例如，FreeRTOS 的互斥锁支持优先级继承：临时提高持锁任务的优先级，帮助它尽快运行并释放锁。这能缓解问题，但不能代替对等待时间的分析。[4]

> **一句话听懂**：优先级再高，如果等的资源迟迟不释放，任务仍然跑不起来。

## 怎样判断控制周期是否可靠

### 周期、执行时间与截止时间

控制周期（Control Period）规定计划每隔多久触发一次控制更新；截止时间规定这次更新最晚何时完成。两者需要按控制要求分别确定。

以“每 2 ms 触发一次，并要求在下一次触发前完成”为例，一次更新可用的时间就是 2 ms。任务实际占用处理器进行计算和处理的时间，称为执行时间（Execution Time）；等待运行、被其他任务或中断打断，也会推迟最终完成的时刻。

假设任务自身需要 1.2 ms，等待运行和被其他工作占用的时间合计又有 0.9 ms，那么从触发到完成就用了 **1.2＋0.9＝2.1 ms**，已经错过这次更新的截止时间。仅看“计算只花了 1.2 ms”，就会漏掉问题。这段从触发到完成的时间，称为响应时间（Response Time）。

因此，要检查的是一次更新能否在规定时限内完成，不能只看平均耗时。最坏执行时间（Worst-case Execution Time，WCET）指任务在规定条件下可能占用处理器的最长时间，它是分析能否按时完成的重要依据。[1]

实测可以发现超时，并得到测试中出现的最大耗时；但这个最大值不代表所有情况下的最坏值。还需要考虑测试没有覆盖的执行路径、并发任务和资源等待。

G1 的官方低层例程中，`CreateRecurrentThreadEx(..., 2000, ...)` 把相关周期线程的间隔设置为 2000 µs，也就是 2 ms。[5] 这个设置说明程序希望按什么节奏运行；是否每次都按时触发、按时完成，还要结合运行环境和实际记录判断。

> **一句话听懂**：每隔 2 ms 触发一次，只是规定了节奏；能否按时完成，还要算上计算、中断和等待占用的时间。

### 怎样找出迟到的原因

[3.4 节](./04-real-time-communication-and-buses.mdx)区分了延迟与抖动。软件里也要分开看：每次都稳定地晚一段时间，需要检查整条处理流程的耗时；偶尔突然晚很多，则要留意那一刻是否有长中断、锁等待或其他任务集中运行。

可以用同一时间基准，记录采样完成、任务触发、计算开始与结束、命令发出等时刻，把同一次更新串起来看。这样才能区分：是任务没有及时开始，还是计算本身太慢，或是算完以后又等了很久。

记录日志也会花时间。实时任务里可以先保存必要的时间戳和结果，再交给低优先级任务整理、输出，避免排查问题的代码反过来拖慢控制。

## 程序卡住后怎样恢复

看门狗（Watchdog）用计时器监督程序运行。软件需要在规定时间内刷新计时器，俗称“喂狗”；如果迟迟没有刷新，就会触发复位等预设动作。

喂狗应建立在关键任务正常完成的检查之上。若只是让某个定时中断不停喂狗，即使控制任务已经卡住，看门狗也可能察觉不到。

重新启动后，软件应先读取硬件记录的复位原因，检查设备状态，再按恢复流程决定是否重新使能执行器。哪些复位信息能被保留，取决于芯片和供电设计。

恢复流程也需要明确的状态。例如，上电后先初始化，检查通过后才允许运行；出现故障后进入相应的保护状态，满足恢复条件才能继续。用状态机（State Machine）明确每个状态允许的动作和切换条件，可以避免程序一重启就沿用故障前的输出。具体状态与保护流程见 [3.6 节](./06-electrical-safety-and-protection.mdx)。

> **一句话听懂**：看门狗帮助发现程序未按要求继续运行；复位之后，软件还要检查状态，再按流程恢复控制。
