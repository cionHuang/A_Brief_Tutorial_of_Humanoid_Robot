## 先看一个现场问题

机器人在仿真中能够稳定运行，换到真实控制板后却偶尔出现一个周期的关节目标滞后；示波器看到 PWM 仍在输出，日志里的主循环也没有崩溃。继续排查发现：高优先级中断占用了控制任务的时间，通信接收缓冲区发生覆盖，温度保护任务又和控制任务竞争同一把锁。

现场通常会这样问：

> “这段代码应该放在 MCU、驱动器还是上位机？2 ms 的控制周期到底是目标、平均值还是最坏情况？任务超时、看门狗复位和急停之后，系统应该回到什么状态？”

嵌入式软件（Embedded Software）运行在资源受限、接口固定并且需要及时响应的计算平台上。实时系统（Real-time System）关心的不只是“算出了正确结果”，还关心结果是否在规定的截止时间（Deadline）前产生。对人形机器人来说，控制周期、执行时间、优先级、中断、缓冲和故障状态共同决定了低层闭环能否可靠工作。

## 计算平台各自负责什么

### MCU、DSP、SoC 与工控机

微控制器（Microcontroller Unit, MCU）通常把 CPU、片上存储器、定时器、PWM、ADC、通信外设和 GPIO 集成在一颗芯片中。它适合运行电机控制、传感器采样、保护逻辑和通信协议等确定性较强的任务。

数字信号处理器（Digital Signal Processor, DSP）针对乘加、滤波、变换和控制算法进行了优化，常用于电机驱动器或高速信号处理。现代 MCU 也可能集成 DSP 指令、浮点单元（Floating Point Unit, FPU：专门做浮点运算的硬件，把很大和很小的数按浮点格式算得又快又准）和电机控制外设，因此“MCU”和“DSP”是功能定位，不一定对应两种完全不同的硬件。

片上系统（System on Chip, SoC）把多个处理单元、存储控制器和高速接口集成在一起，常见于运行 Linux、视觉算法或机器人中间件的计算模块。工控机（Industrial PC, IPC）和边缘计算平台（Edge Computing Platform：装在机器人本地、比云端更近的算力）通常拥有更大的内存和更强的 CPU/GPU，适合规划、感知、日志和模型推理，但其通用操作系统调度和设备驱动不天然提供硬实时保证。

可以先用一条分工线索建立直觉：

| 平台 | 典型任务 | 主要约束 |
| --- | --- | --- |
| 电机驱动 MCU/DSP | 电流环、PWM 更新、编码器采样、过流保护 | 周期短，必须有确定的中断和保护路径 |
| 关节或控制板 MCU | 位置/速度伺服、温度监测、总线收发 | 外设资源和片上内存有限 |
| 实时控制器/SoC | 多关节协调、状态估计、低层命令转发 | 需要控制线程、通信线程和故障线程隔离 |
| 工控机/边缘计算平台 | ROS 2、规划、感知、记录和模型推理 | 延迟和抖动受操作系统、驱动及负载影响 |
| GPU | 图像处理、深度网络和 VLA 推理（见 5.6） | 吞吐量高，但单次执行时间和资源争用需测量 |

这不是固定的硬件架构。同一台机器人可能把多个功能合并在一块 SoC 上，也可能把每个执行器的控制环放在独立驱动器中。判断边界时，应看采样点、执行器输出点、故障切断路径和通信接口，而不能只看设备名称。

> **一句话听懂**：机器人身上有好几种“大脑”：MCU 是小而快的“手脚神经”，专门盯电机和传感器；SoC、工控机是干重活的“大电脑”，负责看路和规划。电脑再强也不保证准点，实时的事得靠小的那颗。

## MCU 如何连接真实硬件

### GPIO、ADC、PWM 与定时器

通用输入输出（General-purpose Input/Output, GPIO）用于读取数字开关、霍尔信号、急停输入和状态脚，也可控制继电器、使能脚或指示灯。模数转换器（Analog-to-Digital Converter, ADC）把电流、电压、温度和压力等模拟量转换成采样值；量程、参考电压、采样时间、分辨率和校准决定了读数质量：参考电压是电压测量的上限，也就是满格对应多少伏；分辨率是用多少位表示，12 位就把量程分成 4096 份（具体位数随型号变化）；校准是用已知标准修正芯片的实际偏差。

脉宽调制（Pulse-width Modulation, PWM）通过改变周期内的导通比例控制逆变器或其他功率器件（PWM 的细节见 3.2）。电机控制通常由定时器产生互补 PWM（两路反相的开关信号，专门驱动上下桥臂）、死区时间和同步触发信号，再由 ADC 在指定的载波相位采样电流。PWM 频率、ADC 采样时刻和控制算法执行时刻应一起设计，否则采样值可能对应上一个开关周期或受到开关噪声污染。

定时器（Timer）负责产生控制周期、输入捕获（记录外部脉冲到达的时刻）、编码器计数和输出比较（到达设定时刻就翻转输出）事件。与软件循环中调用 `sleep` 相比，硬件定时器更适合提供稳定的周期基准；但定时器中断本身也必须短小，复杂计算应交给可调度任务。

> **一句话听懂**：这四个是 MCU 的“手眼”：GPIO 看开关和急停，ADC 把电流、温度这些模拟量翻译成数字，PWM 决定给电机通多少电，定时器负责喊“时间到了、该算下一拍了”。

### DMA、中断与缓冲

直接存储器访问（Direct Memory Access, DMA）可以在外设和内存之间搬运 ADC、UART、SPI 或 EtherCAT 数据，减少 CPU 逐字节处理的负担。常见做法是使用双缓冲或环形缓冲：DMA 写入当前缓冲区，控制任务读取已经完成的上一块数据，并通过序号或标志位确认数据边界。

中断（Interrupt）用于通知 CPU 某个硬件事件已经发生，例如 ADC 转换完成、编码器捕获或通信帧到达。中断服务函数（Interrupt Service Routine, ISR）应只完成时间敏感且可快速完成的工作；把日志格式化、动态内存分配或复杂运动学计算放进 ISR，会增加其他中断和控制任务的最坏响应时间。[3]

缓冲（Buffer）不是 CPU 的缓存（Cache），它解决生产者和消费者速度不一致的问题，但缓冲越深不一定越好。低层控制通常要优先使用最新一帧命令，并丢弃已经过期的旧目标；参数、诊断和日志则可以使用较深队列。每个缓冲区都应记录长度、序号、时间戳和校验结果，避免把半帧或旧帧交给控制器。

> **一句话听懂**：DMA 是 MCU 的“搬运工”，数据来了自己搬进内存，不用 CPU 一字节一字节处理；中断是“门铃”，有事才叫一声；缓冲是“暂存筐”，但要保证机器人拿到的是最新那份，而不是压筐底的旧货。

### 看门狗与故障复位

看门狗（Watchdog）是由硬件或独立计时器监督软件运行的机制。主任务只有在完成关键检查后才能“喂狗”；如果任务死锁、优先级饥饿、时钟异常或程序跑飞，超时会触发复位或进入安全状态。看门狗不能代替急停和硬件过流保护，因为它的动作通常存在毫秒到秒级延迟，且复位并不等于能量已经切断。

复位原因应保存在掉电不丢失的寄存器或诊断区域中，例如区分上电复位、看门狗复位、欠压复位和软件请求复位。重新启动后，系统需要先读取上次故障原因，再决定是否允许重新使能执行器。

> **一句话听懂**：看门狗是“盯着程序干活的闹钟”：程序要按时报到、证明自己还活着；卡死了就强制重启。但它只能重启软件，不能代替急停——真正切断能量还得靠硬件。

## 裸机与 RTOS

### 裸机循环（Bare-metal Superloop）

裸机系统没有通用操作系统，程序通常由一个初始化阶段加一个 `while(1)` 主循环组成：初始化时钟、GPIO、ADC、PWM、通信和保护输入；之后每一圈依次读取采样、运行控制计算、更新输出并处理故障，再回到循环开头。

这种结构的优点是开销小、执行路径容易追踪，适合非常小的控制器。缺点是任务数量增加后，轮询顺序会把低优先级工作拖入关键路径；某个函数执行过久，也会阻塞所有后续任务。裸机并不自动等于硬实时，仍然需要测量每次循环的最坏执行时间。

> **一句话听懂**：裸机就是“一个无限循环从头跑到尾”：读一遍传感器、算一遍控制、更新一遍输出，再从头来。简单直接，但哪一步慢了后面都得等它，所以照样要量“最慢那一圈”够不够快。

### RTOS、任务与优先级

实时操作系统（Real-time Operating System, RTOS）提供任务（Task/Thread）、优先级、阻塞等待、队列、信号量、定时器和内存管理等机制。[4]一个典型的机器人控制板可能划分为：

| 任务 | 触发方式 | 关注点 |
| --- | --- | --- |
| 控制任务 | 硬件定时器或高精度周期 | 固定周期、短执行时间、无阻塞 |
| 采样任务 | ADC/DMA 完成事件 | 数据边界、校准和时间戳 |
| 通信任务 | 接收中断唤醒 | 校验、序号、超时和缓冲区 |
| 保护任务 | 周期检查或硬件事件 | 过流、过温、欠压和失联 |
| 诊断/日志任务 | 低优先级周期 | 不得占用控制路径的锁和带宽 |

任务优先级应由截止时间和安全后果决定，而不是由代码文件大小决定。控制任务等待日志任务释放互斥锁（Mutex：同一时刻只允许一个任务访问的锁）时，会出现优先级反转（Priority Inversion）；可以使用优先级继承、无锁交换缓冲或单写者数据结构降低这种风险。

队列适合传递离散事件和有序消息；共享内存适合高频状态，但必须定义读写一致性。对于一帧包含多个关节状态的数据，建议使用“写入备用缓冲区、完成后一次性切换指针”的方式，避免控制器读到一半更新的数据。

> **一句话听懂**：RTOS 就像给控制板派了几个“专人”：分别管控制、采样、通信和保护，谁更急谁优先。急事不容易被杂事挡住，但几个人争同一把锁时也会互相卡住。

## 怎样判断控制周期是否可靠

### 周期、执行时间与截止时间

控制周期（Control Period）是相邻两次控制更新之间的目标时间间隔。执行时间（Execution Time）是一次任务从开始到完成所花的时间。若周期为 $T$，任务最坏执行时间为 $C$，还要给中断、通信和调度留出余量，则至少应满足：

$$
C + C_{\mathrm{interrupt}} + C_{\mathrm{scheduling}} < T
$$

式中三个量的单位要一致（通常用 ms）；$C_{\mathrm{scheduling}}$ 包含任务切换和中断延迟。这个不等式只是必要条件，最坏情况必须逐周期实测。周期平均值达标并不充分。偶发的一次超长执行时间（长尾）可能错过截止时间，造成旧目标保持、队列堆积或状态估计跳变。工程验证应记录周期误差、最大执行时间、最小/最大空闲时间和连续超时次数。[1]

官方 G1 低层例程 `g1_ankle_swing_example.cpp` 就是一个具体例子：它用 `CreateRecurrentThreadEx(..., 2000, ...)` 建立 2000 µs（2 ms，即 500 Hz）的周期线程；例程维护 29 个电机（`G1_NUM_MOTOR = 29`），在 `LowCommandWriter` 里逐拍写 `LowCmd_` 并做 CRC32（循环冗余校验，Cyclic Redundancy Check）校验。[5] 这正好说明“控制周期是目标还是最坏情况”，必须靠实测回答。

> **一句话听懂**：“控制周期”是每隔多久算一拍，“执行时间”是这一拍算完用了多久。要求不只是平均够快，而是最慢那一次也得赶在下一拍到来前算完——像赶班车，偶尔没赶上就误事。

### 固定延迟与抖动要分开治

[3.4 节](../03-electrical-embedded/04-real-time-communication-and-buses.mdx)已经给过周期抖动（Period Jitter）与端到端延迟（End-to-end Latency）的定义。落到实时软件这一层，要紧的是**把两者分开看**：周期很稳定、但每帧都固定延迟，和平均延迟很小、却忽快忽慢，是两种不同的毛病——前者可以靠时序预算与提前量补偿，后者只能靠隔离负载、锁住优先级、减少共享资源来压。

应使用单调时钟记录关键节点：采样开始、DMA 完成、控制计算开始/结束、命令发送、执行器确认和故障触发。日志本身不能阻塞实时任务，必要时先写入无锁环形缓冲，再由低优先级任务异步导出。

> **一句话听懂**：固定延迟可以靠提前量补回来，抖动只能靠隔离与优先级治理——两者要分开测、分开治，别用一个平均延迟糊过去。

### 优先级反转与资源争用

优先级反转（Priority Inversion）的成因是：高优先级控制任务在等低优先级任务持有的锁，而中优先级任务不断抢占 CPU，把低优先级任务挤得迟迟不能释放锁，结果最急的任务反而被堵住。类似问题也会出现在共享总线、缓存、浮点单元、GPU 或内存带宽上。解决方法包括缩短临界区、避免控制任务进行阻塞 I/O、为实时任务预留 CPU 时间，以及把诊断和大块数据传输移到独立通道。[2]

> **一句话听懂**：优先级反转就是“最急的人反而被堵住”：急任务在等一把被慢任务拿着的锁，中间不急不慢的任务还一直插队。办法是让锁用得尽量短，或让急任务用自己的一份数据，不跟别人抢。

## 从上电到故障恢复的状态机

软件侧要把模式切换实现成显式状态机，每个状态有明确的进入/退出条件、超时和动作输出。完整的状态划分、`FAULT_LATCHED` 锁存语义与恢复流程见 [3.6 节](../03-electrical-embedded/06-electrical-safety-and-protection.mdx)。
