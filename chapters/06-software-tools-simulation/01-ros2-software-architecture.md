# 6.1 ROS 2 与机器人软件架构

## 先看一个现场问题

团队把状态估计、规划器和控制器分别调试好之后接上 G1：RViz 2 里的模型却趴在地上：TF 树里 `pelvis` 的父坐标系接错了。终端反复报 "extrapolation into the future"，原因是某个节点在用过期时间戳查询坐标变换。机器人偶尔抽一下，排查后发现有两个节点同时往同一个命令 Topic 发数据。每个模块单独测试都是对的，连起来全是问题。

现场通常会这样问：

> “每个节点单独跑都对，为什么连起来就乱？到底谁在发指令、谁说了算？这个坐标变换、这条命令应该归哪个节点管？”

这三个现象在本节各有回收点。`pelvis` 父坐标系接错，对应“TF”一节的树断裂与成环。`extrapolation` 对应同一节的缓存越界。两个节点抢同一个命令 Topic，对应“先看全局”的“命令只有一个出口”和“ros2_control”的资源仲裁。

> **一句话听懂**：问题往往不在单个模块，而在模块之间没有约定——坐标谁说了算、命令谁发、时间以谁为准。

大脑层的每一个判断，最终都要落到具体软件与工具上。本章按“怎么组织软件（6.1）→ 在哪个仿真器里跑（6.2–6.4）→ 用哪些库（6.5）→ 怎么保证可复现（6.6）”展开。

## ROS 2 是什么、为什么机器人要用它

机器人不是一个大程序。一台 G1 上同时跑着状态估计、足步规划、全身控制、感知、遥操作、录包和可视化：它们由不同的人用不同的语言写成，更新节奏从几赫兹到上千赫兹，任何一个模块崩溃或重启都不应该把整机拖死。手工用管道、共享内存或自定义 socket 把这些模块焊在一起，短期可行，长期会卡在三件事上：接口没有契约（改一个字段就要所有模块重编）、时间与坐标没有统一来源（各模块各自换算）、生态无法复用（导航、可视化、仿真、录包都得自己写）。中间件（Middleware）解决的正是“进程之间按什么约定说话”这一层——ROS 2（Robot Operating System 2）就是机器人领域主流的中间件，名字里的“操作系统”容易误导。[1][5]

它的价值可以拆成四条：

- **进程解耦**：每个模块是一个独立进程（节点，Node），单独编译、单独启动、单独重启，感知节点崩溃不会带着控制器一起退出；
- **语言无关**：C++、Python 节点只要消息定义一致就能互通，算法侧用 Python，实时侧用 C++；
- **生态复用**：导航（Nav2）、坐标变换（TF2）、控制框架（ros2_control）、录包回放（rosbag2）、可视化（RViz 2、Foxglove）和仿真桥都有现成组件，不必重造；
- **分布式**：节点可以跨主机、跨网卡运行，机载计算机和操作台按 Topic 连接，不需要把所有算力都塞进一个盒子。

**ROS 2 不是一个程序，而是若干可以单独取用的组件，外加一套约定。** 各组件的基本分工是：

| 组件 | 负责什么 | 本节位置 |
| --- | --- | --- |
| 通信方式（Topic/Service/Action/Parameter） | 进程之间传数据 | “四种通信方式” |
| TF2 | 坐标变换的单一事实来源 | “TF” |
| ros2_control | 硬件与控制器之间的标准接口 | “ros2_control” |
| rosbag2 与节点日志 | 记录、回放与事后复盘 | “观测与调试” |
| 可视化（RViz 2 / Foxglove） | 空间关系与时间序列检查 | 6.4 节 |
| RMW 与 QoS | 选择底层 DDS 实现与投递策略 | 3.4 节 |

严格说，TF2、ros2_control 是跑在 ROS 2 通信层之上的功能包和框架，rosbag2 与可视化是工具；它们的共同底座是同一套约定：消息定义（`.msg`/`.idl`）、命名与命名空间、时间戳语义、坐标命名。把 ROS 2 理解成“一套东西”会带来一个典型误判：以为用了 Topic 就必须用 TF、用了 ros2_control 就必须录包，实际上每一件都可以单独引入。

**边界：毫秒级闭环不放在 ROS 2 里跑。** ROS 2 节点是普通操作系统进程，调度、内存分配、序列化和 DDS 传输都会引入抖动，端到端延迟和抖动在微秒到毫秒量级，且不保证最坏执行时间。4.5 节的关节力矩/阻抗闭环、4.6 节的全身控制（Whole-Body Control, WBC）通常要求 1–2 ms（常见 500 Hz～1 kHz）的确定性周期，因此它们跑在实时线程、共享内存或厂商 SDK 的底层循环里，而不是跑在 ROS 2 的 Topic 回调里。ROS 2 的主要职责是 1–100 Hz 的规划与编排、状态汇总、参数与可视化——正是 5.3 节频率分层中的大脑层和规划层那几档。把 WBC 挂进普通 ROS 2 节点通常不报错，只是偶尔丢一个周期，然后机器人抽一下。

> **一句话听懂**：ROS 2 不是操作系统，也不是一个程序，而是“可单独取用的组件 + 一套消息与命名约定”；它管 1–100 Hz 的规划与编排，毫秒级闭环仍然跑在实时线程和底层 SDK 里。

## 先看全局：一条指令的软件路径

把本节后面所有内容放进一张架构图，一条指令从任务到关节的路径是：

```text
任务/行为层 → 规划器 → 控制器（WBC/关节）→ 硬件接口 → SDK/总线 → 驱动器
     ↑            ↑          ↑                  ↑
   感知系统   状态估计    状态估计          状态上报（LowState/JointState）
```

后面几节就挂在这条路径上：通信方式决定箭头之间传什么样的数据，TF 决定位姿和时间怎么对齐，ros2_control 对应“硬件接口”那一段，可观测性决定怎么把整条链路录下来复盘；SDK/总线那一段的设备侧细节在 3.4 节（总线与 DDS）与厂商 SDK（[7]）里。

划边界的三条原则：

1. **状态只有一个估计来源**：姿态、速度的“权威版本”由状态估计模块（4.4 节）发布，其他模块消费而不是各自重算；
2. **命令只有一个出口**：任何时刻只允许一个模块拥有对底层的命令权，切换（例如导航接管、遥操作接管、安全降级）必须显式，这正对应 ros2_control 的资源仲裁思想；
3. **时间基准全局一致**：所有消息带时间戳，跨模块的融合和控制按测量时间对齐。

频率分层与 5.3 节的表一致：行为层秒级、规划层几十赫兹、控制层百赫兹以上；把这些不同节奏的模块塞进一个进程一个线程，是新人最常见的架构错误。

> **一句话听懂**：划边界就三条：状态只有一个估计来源、命令只有一个出口、时间基准全局一致；后面所有小节都是这条路径上的具体分工。

## 四种通信方式：按数据形态选型

### 节点与四种交互方式

节点（Node）是独立运行的进程单元。节点之间的交互有四种基本形态（ROS 2 文档里叫 Communication Primitives，这里就直说“四种方式”），选型的依据是数据形态而不是习惯：[1][2]

| 方式 | 形态 | 典型用途 |
| --- | --- | --- |
| Topic | 持续发布/订阅，多对多，无应答 | 关节状态、IMU、点云等流式数据 |
| Service | 一次请求一次应答 | 查询参数、触发标定等短操作 |
| Action | 长任务：目标 + 持续反馈 + 可取消 | 导航到某点、执行一段轨迹 |
| Parameter | 节点自有的可配置值 | 增益、阈值、坐标系名称 |

把持续流数据塞进 Service 会压垮请求方；把需要确认完成的长任务塞进 Topic 会让调用方无法知道成败。Topic 背后的 QoS（Quality of Service，可靠性、历史深度、延迟预算）属于 DDS 概念，3.4 节已经详细讲过，本节不重讲；这里只补一条 ROS 2 侧的失败模式：QoS 不匹配时，两个节点通常“都能发现彼此、也都在发布”，但数据就是收不到，而且不一定报错。[1]

> **一句话听懂**：选通信方式看数据形态：连续流用 Topic、短问答用 Service、长任务用 Action、配置用 Parameter；用错不是性能问题，是语义问题。

### Launch、生命周期与实时性

启动文件（Launch）描述一组节点如何启动、参数如何注入；部分节点还有受管生命周期（Managed Lifecycle）：未配置、未激活、激活、销毁等状态显式转换。它的价值在于把“系统是否就绪”变成可查询的状态，而不是靠启动后 sleep 几秒赌运气。

节点默认各自运行在独立进程里，消息经 DDS 传输：进程边界带来隔离，也带来序列化和跨进程拷贝的开销。节点组合（Node Composition）允许把多个节点加载进同一个进程、共用同一个执行器（Executor），数据以进程内指针传递，省掉中间拷贝；代价是一荣俱荣、一损俱损——一个节点崩溃或阻塞会拖住同进程的其它节点。执行器决定回调在几个线程上、以什么顺序执行：单线程执行器确定性好，但会被慢回调卡住；多线程执行器吞吐高，但回调并发访问共享状态必须显式加锁，否则就是数据竞争和偶发抽动。

那能不能干脆上实时？ROS 2 支持实时调度、内存预分配和零拷贝，但一个普通 Linux 用户态进程无法保证最坏执行时间（Worst-Case Execution Time, WCET）。所以高频控制不放在普通节点里：要么把控制循环做成独立实时线程，通过共享内存或 `ros2_control` 的实时 Hardware Interface 更新，ROS 2 只负责参数下发和状态汇总；要么把控制留在厂商 SDK 的底层循环里，ROS 2 侧只做非实时桥接。把 1 kHz 的控制回调直接挂在普通执行器上，典型现象不是报错，而是偶发丢周期、时间戳抖动，然后机器人抽一下。注意：它的外观和开头那句“机器人偶尔抽一下”一样，但根因不同——那边是**两个节点抢同一个命令通道**，这里是**调度抖动**。排查时不能只看现象，要回到“命令谁在发”和“周期是否稳定”这两个问题。

> **一句话听懂**：Launch 决定谁启动、带什么参数，受管生命周期把“系统就绪了吗”变成可查询的状态；节点组合和执行器决定隔离与开销的取舍，而高频控制不能靠普通节点和执行器兜底。

## TF：坐标变换的单一事实来源

TF2（Transform Library 2）维护一棵随时间变化的坐标变换树：广播器（Broadcaster）持续发布变换，监听器（Listener）把变换缓存进缓冲区（Buffer），任何节点都可以查询“过去某一时刻 A 坐标系到 B 坐标系的变换”。[3]

三个高频故障都和时间有关：

- **时间戳不一致**：用 $t = 0$（最新可用）和用消息自带时间戳查询，结果可能完全不同；4.4 节“时间不是附属字段”在 TF 查询上同样成立；
- **外推错误**：查询的时刻超出缓存范围（过去太久或未来），通常意味着某一路变换的发布频率不足或时钟不同步；
- **树断裂或成环**：`pelvis` 接错父坐标系、两个节点都声称自己是同一个变换的广播者，模型在 RViz 里就会趴下或散开。

坐标命名和约定遵循 REP-103（单位与右手系）和 REP-105（`map`/`odom`/`base_link` 等标准坐标系）。[6] 对 G1，TF 树通常覆盖 `pelvis`、`torso_link`、各关节 link 和 IMU 固定 link（见 4.4 节的模型核对）；关节角到各 link 位姿的正运动学变换由 robot_state_publisher 根据 URDF 和 `JointState` 消息自动完成。

> **一句话听懂**：TF 是坐标变换的唯一事实来源：所有模块查同一棵树，而不是各自换算；时间戳不一致、外推越界、树断成环，最后都表现为模型在 RViz 里趴下或散开。

## ros2_control：硬件与控制器之间的标准接口

ros2_control 把“读写硬件”和“控制算法”拆成两层，中间用显式接口连接：[4]

- **Hardware Interface**：每个执行器/传感器声明自己暴露的状态接口（State Interface，如 `position`、`velocity`）和命令接口（Command Interface），由具体的硬件组件（Hardware Component）实现读写；
- **Controller**：控制器只面向接口编程——PID、轨迹控制器不知道也不关心背后是 G1、机械臂还是仿真器；
- **Broadcaster**：一种特殊控制器，只负责把状态接口转成消息发出去，例如 `joint_state_broadcaster`；
- **Controller Manager**：统一管理控制器的加载、激活、切换和硬件资源仲裁——同一时刻一个命令接口只能被一个激活的控制器占用，这从框架层面回答了“谁在发指令”。

资源仲裁是这套架构的核心价值：两个控制器同时写同一个关节，在传统手写代码里是运行时才暴露的隐患，在 ros2_control 里是启动切换时就报错的设计错误。

> **一句话听懂**：ros2_control 把“读写硬件”和“控制算法”拆开、中间用显式接口连接；它的核心价值是资源仲裁——同一时刻一个命令接口只能有一个激活控制器。

## 观测与调试：rosbag2 与日志

可观测性是架构的一部分，不是事后补丁。ROS 2 侧主要靠两件工具：

- **rosbag2**：按 Topic 记录原始消息，回放（Playback）时可以原速、倍速或按时间戳精确复现一次故障。它记录的是消息层，不记录实时域内部的闭环变量；要让一次抽动可复盘，就得把桥接前后的关键量都录下来——低层 `rt/lowstate` 的关节与 IMU、桥接后的 `JointState` 与 `Imu`、控制器内部误差，缺一段就只能靠猜。记录的第一原则是先记录再分析，“当时没开 bag”是机器人调试里代价最高的四个字；
- **日志**：节点日志应带级别和时间，关键状态切换、命令仲裁结果、QoS 不匹配告警和降级触发必须可回溯（呼应 3.6 节的故障语义）。日志不要写进实时线程，桥接节点里一次磁盘阻塞就足以打乱控制周期。

空间关系看 RViz 2、时间序列看 Foxglove，两者的分工与用法是 6.4 节的整节主题，本节不展开。4.4–4.6 节与 5.3 节每一节的排查清单，最终都落在这组 bag 记录里“这条曲线长什么样”。

> **一句话听懂**：可观测性靠两件事——rosbag2 按 Topic 把消息录全、日志把状态切换记清楚；“当时没开 bag”是调试里代价最高的四个字；空间看 RViz 2、时间序列看 Foxglove，详见 6.4 节。
