## 先看一个现场问题

把 G1 的 URDF 直接拖进 MuJoCo：机器人加载出来了，却像布娃娃一样瘫在地上——URDF 里没有执行器定义。换成官方 MJCF 后机器人能站了，但控制循环一发“位置指令”就抽搐——`g1_29dof.xml` 里的执行器是力矩电机，期望的是力矩而不是目标位置。足底接触地面时偶尔还会穿透或弹跳，换了一个场景文件，模型又加载失败，提示找不到网格文件。

现场通常会这样问：

> “同一个 G1，为什么在 MuJoCo 里的表现和文档里不一样？`ctrl` 到底该给位置还是力矩？脚底穿透是模型错了还是参数错了？”

这四个现象在本节各有回收点：

- URDF 变布娃娃：对应“MJCF 的建模元素”里执行器的缺失（URDF 没有执行器定义）；
- 发位置指令却抽搐：对应同一节“Actuator”里 `ctrl` 的语义由执行器类型决定；
- 足底穿透或弹跳：对应“Body、Joint 与 Geom”里的接触参数 `solref`/`solimp`/`friction`；
- 找不到网格：对应“先看全局”里 `meshdir` 与相对路径的组织方式。

> **一句话听懂**：MuJoCo 根据模型和控制输入计算机器人怎样运动、怎样接触环境；MJCF 写清模型结构、执行器和仿真参数。

> **在整机里的位置**：这一节属于“横向基础设施：仿真与工具”；上游是模型与控制指令，下游是策略验证与部署。总图见 [1.3 节](../01-system-overview/03-humanoid-robot-system-architecture.mdx)。

## MuJoCo 是什么、为什么用它

MuJoCo（Multi-Joint dynamics with Contact）是面向“接触富集”任务（contact-rich tasks：成败主要取决于接触力的一类任务，比如抓取、足底支撑）的物理仿真器，也是腿式机器人策略做 Sim2Sim 验证的常用环境。[1] 它和一般刚体仿真器最不一样的地方是接触模型：MuJoCo 用软接触（soft contact），把碰撞当成可穿透的弹簧—阻尼系统求解，而不是把接触当成不可违背的硬约束；足底、手指这类持续接触的场景因此数值上更稳。它只用 CPU 就能跑，单次仿真的确定性与可复现性好，开源并由 Google DeepMind 维护。[1][2]

本教程把 MuJoCo 用于控制实验和 Sim2Sim 验证，把 Isaac Sim / Isaac Lab 用于 GPU 并行训练与视觉在环（[6.3 节](./03-isaac-sim-isaac-lab.mdx)），把 Gazebo 用于 ROS 2 集成与场景搭建（[6.4 节](./04-gazebo-rviz2-foxglove.mdx)）。这是本书采用的工作流；MuJoCo 也支持策略训练，MJX 提供加速器上的并行仿真。[5]

在本书里，MuJoCo 有四个具体用途：

- 跑本手册保留的 G1 模型（`g1_29dof.xml` 等三个变体）；
- 验证训练出来的策略，就是 [5.5 节](../05-brain-perception-planning-vla-wam/05-learning-control-and-imitation-learning.mdx)的 Sim2Sim 链路；
- 与工具库交叉验证动力学（[6.5 节](../06-software-tools-simulation/05-kinematics-dynamics-libraries.mdx)）；
- 做不需要 GPU 的控制实验（本节最后一节）。

需要进一步了解 GPU 并行训练和视觉环境搭建，可继续读 [6.3 节](./03-isaac-sim-isaac-lab.mdx)。

## 先看全局：模型由哪几部分组成、最短跑通路径

一次 MuJoCo 仿真跑起来，只需要三件东西：

- **机器人模型文件（MJCF）**：只描述机器人本身，本手册保留 `g1_29dof.xml`、`g1_29dof_lock_waist.xml`、`g1_29dof_with_hand.xml` 三个变体；
- **场景文件 `scene.xml`**：描述模型之外的世界——地面、光照和相机视角，用 `include` 把机器人模型拼进来；
- **网格目录 `meshes/`**：存模型引用的 STL 网格，路径由 `<compiler>` 元素的 `meshdir` 指定。

<MjcfFieldSnippet variant="scene" />

按下面四步跑通一次仿真：

1. **选模型、改 `include`**：当前 `scene.xml` 里写的是 `include file="g1_12dof.xml"`，而本手册只保留了 `g1_29dof` 系列三个变体，所以第一步就是把它改成目标模型文件名；
2. **加载后核对 `nq`/`nv`/`nu`**：这三个是模型的维度（位置、速度与执行器的个数）。以 `g1_29dof.xml` 为例是位置 7+29、速度 6+29、执行器 29；换变体后可以按同一个通式快速复核（只适用于浮动基座 + 单自由度关节的模型）：位置 = 7 + 关节数、速度 = 6 + 关节数、执行器 = 关节数（锁腰变体 34/33/27，带手变体 50/49/43）；球关节、固定基座或闭链会让 `nq` 偏离这个通式，这时以模型文件为准；
3. **用 `mj_step` 推进**：按固定仿真步长一步步向前积分；
4. **读 `sensordata`**：从 `mj_data` 里取传感器读数，和期望行为对照。

`<compiler angle="radian" meshdir="meshes"/>` 规定了角度单位与网格目录；移动模型文件时必须保持 `meshes/` 的相对位置不变，否则加载报找不到 STL。

<MjcfFieldSnippet variant="compiler" />

后面几节就挂在这条链上：MJCF 的建模元素决定模型怎么被描述，Actuator 决定 `ctrl` 怎么被解释，场景与加载决定它能不能跑起来，加载检查清单决定跑得对不对，控制实验是拿它来做什么。

## MJCF 的建模元素

### Body、Joint 与 Geom

MJCF 用 `<body>` 的嵌套层级表达运动树，每个 body 内挂 `<joint>`（运动关系）、`<geom>`（碰撞与可视化几何）和 `<inertial>`（动力学参数）。G1 的 `g1_29dof.xml` 中，`pelvis` 上挂着 `floating_base_joint`，类型为 `free`——这就是 [4.3 节](../04-cerebellum-realtime-control/03-dynamics.mdx)“qpos 7+29、qvel 6+29”维度关系的来源：自由关节在位置上占 7 个数（3 平移 + 4 四元数），速度上占 6 个数。加载模型后第一件事应是核对 `nq`、`nv`、`nu` 三个维度与预期一致。[2][3]

<MjcfFieldSnippet variant="bodycore" />

Geom 分 visual 和 collision 两类用途，碰撞几何的形状和摩擦参数直接决定足底接触行为。足底穿透或弹跳通常出在接触求解参数上：MuJoCo 用软接触模型，`solref`/`solimp` 控制接触的刚度与阻尼（它们是求解器用的数值参数，不是可测量的物理量），地面 geom 的 `friction` 决定摩擦锥。这些参数调的是数值行为，与真实地面的摩擦系数之间没有直接等号。

> **一句话听懂**：body 嵌套成运动树，joint 决定它怎么动，geom 决定它怎么碰。

### Actuator：ctrl 的语义由执行器类型决定

开头“发位置指令却抽搐”的根因在这里。`<motor>` 型执行器的 `ctrl` 直接是广义力（作用在某个自由度方向上的力或力矩；对转动关节就是力矩）；`<position>` 型执行器内部自带一个 PD，把 `ctrl` 解释为目标位置。（`ctrl` 是控制输入，每个执行器一路。）`g1_29dof.xml` 定义了 29 个 `<motor>`，每个绑定同名关节，例如 `<motor name="left_hip_pitch_joint" joint="left_hip_pitch_joint"/>`——对 G1 官方 MJCF，`ctrl` 就是关节力矩。[2]

<MjcfFieldSnippet variant="actuator" />

要在这种模型上做“位置控制”，需要在仿真循环外自己实现 PD：用 `qpos/qvel` 读出关节状态，按 [4.5 节](../04-cerebellum-realtime-control/05-basic-control.mdx)的阻抗公式算出力矩写入 `ctrl`，这正是 `unitree_rl_gym` 的 MuJoCo 部署示例（[5.5 节](../05-brain-perception-planning-vla-wam/05-learning-control-and-imitation-learning.mdx)链路）的做法，接口形状与 G1 真机 `MotorCmd_` 的 `kp`/`kd` 一致。[4] 真机的 `kp`/`kd` 由电机固件在自己的周期里执行。迁移参数时，要逐关节核对更新率、限幅和反馈，再验证增益与响应。

> **一句话听懂**：`ctrl` 给的是位置还是力矩，完全由执行器类型决定——`<motor>` 直接吃广义力，`<position>` 内部自带 PD；G1 官方 MJCF 是 29 个 `<motor>`，想要位置控制得在循环外自己写 PD。

### Sensor：带噪声和滤波的仿真传感器

MJCF 的 `<sensor>` 挂靠在 site 上（site 是模型上不带质量、只用来标记位置和坐标系的点）。

<MjcfFieldSnippet variant="site" />

`g1_29dof.xml` 为 `imu_in_pelvis` 和 `imu_in_torso` 两个 site 各配置了一个 `<gyro>` 和一个 `<accelerometer>`，且都带 `noise` 和 `cutoff` 属性——例如陀螺仪 `noise="5e-4"`、加速度计 `noise="1e-2"`。这些仿真参数描述噪声与带宽限制；对应真机的取值由传感器标定确定。[4.4 节](../04-cerebellum-realtime-control/04-state-estimation.mdx)状态估计和 [5.5 节](../05-brain-perception-planning-vla-wam/05-learning-control-and-imitation-learning.mdx)域随机化里“传感器差异”一项，在 MuJoCo 里对应的就是这组参数的调节范围。与 SDK 测量对照时，要统一坐标系与时间，并按标定结果设置噪声和零偏。

<MjcfFieldSnippet variant="sensor" />

## 加载检查清单与常见错误

模型能不能跑起来，先过一遍这张清单：

- **`include` 指向的模型存在**：当前 `scene.xml` 写的是 `include file="g1_12dof.xml"`，本手册只保留 `g1_29dof`、`g1_29dof_lock_waist`、`g1_29dof_with_hand` 三个变体，使用前必须改成目标模型文件名；
- **网格路径对得上**：`<compiler angle="radian" meshdir="meshes"/>` 里的 `meshdir` 按当前 XML 所在目录解析，移动 `scene.xml` 或模型文件时要保持 `meshes/` 的相对位置不变，否则加载报找不到 STL；
- **关节数与命名**：与预期模型一致；
- **`nq/nv/nu` 维度**：对照前文“最短跑通路径”里那组数字逐项打勾即可（通式与变体取值见前文）；
- **IMU 位置**：`imu_in_pelvis` 与 `imu_in_torso` 两个 site 存在且位置合理；
- **碰撞 geom 是否齐全**：足底、膝、肘这些会接触的地方不能只有 visual geom；
- **足底初始是否与地面轻微穿透**：穿透会在第一步触发接触力冲击。

> **一句话听懂**：加载失败大多只出在两处——`include` 指向的模型文件名不对、`meshes/` 相对路径断了；加载成功后先核 `nq/nv/nu`、IMU site 与足底初始穿透，再谈控制。

## 在 MuJoCo 里做控制实验

前面几章的概念都可以在 G1 MJCF 上直接变成实验：

- **位置/力矩控制对比**：给同一关节分别写固定力矩和 PD 位置跟踪，观察响应差异，直观理解 [4.5 节](../04-cerebellum-realtime-control/05-basic-control.mdx)的阻抗接口；
- **踝关节**：按 [2.1 节](../02-mechanics/01-mechanisms-and-dof.mdx) PR/AB 命名的关节索引做摆动实验，复现 [4.5 节](../04-cerebellum-realtime-control/05-basic-control.mdx)的踝摆动示例；
- **重力补偿**：用 `mj_inverse`（逆动力学：给定目标加速度反解所需力矩）或模型重力项算 $g(q)$ 作为前馈力矩，观察机器人是否能“挂”在半空，验证 [4.3 节](../04-cerebellum-realtime-control/03-dynamics.mdx)的动力学参数；
- **接触观察**：开启接触力可视化，双支撑到单支撑切换时观察法向力的重新分配，对应 [2.4 节](../02-mechanics/04-foot-contact-and-stability.mdx)的支撑域和 [4.6 节](../04-cerebellum-realtime-control/06-balance-and-whole-body-control.mdx)的 ZMP；
- **数据记录**：每步从 `mj_data` 取 `qpos`、`qvel`、`sensordata`、接触力和 `ctrl`，带仿真时间戳存盘——格式纪律与 [6.1 节](../06-software-tools-simulation/01-ros2-software-architecture.mdx) rosbag2 相同，先记录再分析。[3]

> **一句话听懂**：前面几章的概念都能在这条最短链上变成实验——位置/力矩控制、踝摆动、重力补偿、接触力观察和数据记录，不需要 GPU，一台笔记本就能跑。
