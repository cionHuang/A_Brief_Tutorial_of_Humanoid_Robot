# 6.6 软件工程与版本管理：代码、模型、参数、固件、数据

## 先看一个现场问题

上周五 G1 还能稳定行走，今天同一份代码跑起来就摔——没人说得清这一周里哪台机器上改过什么。两个工位的仿真结果不一致，排查后发现一个用的是 `g1_29dof.xml`，另一个是锁腰版。实机固件升级后，SDK 消息字段的语义悄悄变了，部署代码按旧约定解析。半年后想复现论文里的实验，训练环境的依赖早已装不回来。

现场通常会这样问：

> “'它上周还能走'这句话，怎么才能变成可以核查的事实？一次实验的结果，到底由哪些东西共同决定？”

机器人系统的行为由五样东西共同决定：代码、模型、参数、固件、数据。只管理代码版本，就只能在五分之一的意义上回答“系统变了没有”。本节把版本管理和可复现性（Reproducibility）扩展到这五个维度，G1 的模型变体和 SDK 版本是最现成的例子。

> **一句话听懂**：“上周还能走”之所以查不清，是因为要同时对齐五样东西——代码、模型、参数、固件、数据；只盯代码，剩下四样随时能把你打回原形。

## 模块边界与配置管理

### 模块划分是版本管理的前提

6.1 节的模块划分——硬件抽象、控制器、规划器、感知、仿真、工具——同时也是版本边界：每个模块有自己的接口契约，接口不变时模块内部可以自由演进。跨模块的任何共享结构（消息定义、关节索引表、坐标系约定）都属于契约层，变更要走显式的评审和版本号，不能顺手改掉。

> **一句话听懂**：模块边界就是版本边界——接口不变，模块内部可以自由演进；消息定义、关节索引表、坐标系约定这类共享结构一变，就要评审加版本号。

### 参数也是代码

关节限位、控制增益、模型参数、传感器标定、仿真配置、环境参数，这些配置直接决定系统行为，应当和代码一样进版本库、走评审、留历史。[3] 工程上实用的分层是：默认参数（机型通用）→ 机型参数（如 G1 29 DoF 无手）→ 现场参数（某次实验的临时调整），三层覆盖关系固定，禁止把现场调整直接写进默认层。参数文件里每一处数值都应能回答“它从哪来”：标定实验、官方文档还是拍脑袋。

> **一句话听懂**：参数和代码一样进版本库、走评审；默认、机型、现场三层覆盖关系固定，现场临时调整不能直接写进默认层。

## 版本管理：不止 Git

### 代码与提交

代码版本用 Git：提交（Commit）要小而有明确意图，里程碑用标签（Tag）标记，版本号遵循语义化版本（Semantic Versioning）：破坏性变更、新增功能、修复分别对应主、次、修订号。[1][2] 机器人项目的特殊性在于“代码”只是五元组里的一项。

> **一句话听懂**：代码版本用 Git——提交要小而有明确意图、里程碑打标签、版本号按语义化版本；但“代码”只是五元组里的一项。

### 模型、固件与数据

完整的系统版本是一个五元组：

| 元素 | 版本载体 | 变更影响 |
| --- | --- | --- |
| 代码 | Git commit/tag | 控制逻辑与接口 |
| 模型 | URDF/MJCF 文件 + 来源提交（见 `third_party/README.md`） | DoF、关节顺序、惯量、碰撞 |
| 参数 | 参数文件进版本库 | 增益、限位、阈值 |
| 固件 | 机器人/驱动器固件版本号 | 消息语义、控制模式、保护行为 |
| 数据 | 数据集版本（采集日期、筛选规则、格式版本） | 训练结果与评估基准 |

模型和固件的坑最隐蔽：G1 从 `g1_29dof` 换成锁腰模型，关节索引、DoF 和重力补偿参数全变；SDK 固件升级可能改变消息字段语义。[4][5]

> **一句话听懂**：模型、参数、固件、数据也都各有版本载体；G1 换模型变体会改关节索引与重力补偿参数，固件升级可能改消息字段语义。 本手册的 `third_party/README.md` 固定上游仓库提交 SHA，正是把“模型来源”变成可核查版本的做法。

### 一次实验的可核查描述

任何实验结果都应能回答：代码哪个提交、模型哪个版本、参数哪份文件、固件什么版本、数据哪一版。写实验记录时把这五项列全，“上周还能走”就变成一次 `git checkout` 加一次参数比对能验证的事实。

> **一句话听懂**：一次实验要能报出五个版本（代码、模型、参数、固件、数据）；写全这五项，“上周还能走”就变成可核查的事实。

## 可复现性

可复现（Reproducibility）的验收标准很朴素：半年后换一台机器，能把实验重跑出来并拿到一致的结果。它要求四件事：

- **环境固定**：依赖版本锁定（lock 文件）或容器镜像固化，训练框架、CUDA、物理引擎版本全部写明；
- **随机种子**：训练与仿真的随机种子记录并固定；要报告的是多种子分布，单次种子的成功不构成结论；
- **日志与数据**：6.1 节和 6.4 节的 rosbag2/日志纪律在这里变成可复现性基础设施——没有原始数据，就无法区分“复现失败”和“记录缺失”；
- **结果归档**：模型权重、评估脚本、环境配置与结果指标一起存档，构成一个可检索的实验单元。

强化学习实验对可复现性最敏感：同样的代码和种子，换 GPU 型号或库版本都可能产生不同结果（5.5 节）。因此 RL 结果的报告单位应该是“种子 × 环境”的分布，而不是单次运行曲线。

> **一句话听懂**：可复现 = 半年后换台机器还能重跑出同样的结果，靠环境锁定、随机种子、日志数据、结果归档四件事；RL 报告的是“种子 × 环境”的分布，不是单次曲线。

回到第 1 章那张五层地图：机械与本体层决定“能怎么动”，电气与嵌入式层决定“动得多准、多快、多安全”，小脑层决定“这一毫秒怎么动”，大脑层决定“去做什么”，而软件与工具链层决定“前面四层能不能被复现、被别人接手”。这本书的每个术语，最终都落在这五层里的某一层上。
