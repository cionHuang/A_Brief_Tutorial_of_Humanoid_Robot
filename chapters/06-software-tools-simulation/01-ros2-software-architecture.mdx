## 各自都能跑，合起来不行

团队把状态估计、规划器和控制器分别调试好之后接上 G1：RViz 2 里的模型却趴在地上：TF 树里 `pelvis` 的父坐标系接错了。终端反复报 "extrapolation into the future"，原因是某个节点在用过期时间戳查询坐标变换。机器人偶尔抽一下，排查后发现有两个节点同时往同一个命令 Topic 发数据。每个模块单独测试都是对的，连起来全是问题。

联调现场通常这样问：

> “每个节点单独跑都对，为什么连起来就乱？到底谁在发指令、谁说了算？这个坐标变换、这条命令应该归哪个节点管？”

这三个现象在本节各有回收点。`pelvis` 父坐标系接错，对应“TF”一节的树断裂与成环。`extrapolation` 对应同一节的缓存越界。两个节点抢同一个命令 Topic，对应“先看全局”的“命令只有一个出口”和“ros2_control”的资源仲裁。

> **一句话听懂**：问题往往不在单个模块，而在模块之间没有约定——坐标谁说了算、命令谁发、时间以谁为准。

> **在整机里的位置**：这一节属于“横向基础设施：中间件”；上游是各层算法节点，下游是硬件接口与总线。总图见 [1.3 节](../01-system-overview/03-humanoid-robot-system-architecture.mdx)。

上层的每一个判断（俗称“大脑”的那部分），最终都要落到具体软件与工具上。本章按“怎么组织软件（6.1）→ 在哪个仿真器里跑（6.2–6.4）→ 用哪些库（6.5）→ 怎么保证可复现（6.6）”展开。

顺带回答一个常见疑问：**没有 ROS 2 行不行？** 行——不少整机厂商用自己的中间件或直接点对点通信。ROS 2 提供的是一套现成的约定和生态；理解了“为什么需要这些约定”，换成别的中间件你也能对上号。

## ROS 2 是什么、为什么机器人要用它

机器人不是一个大程序。一台 G1 上同时跑着状态估计、足步规划、全身控制、感知、遥操作、录包和可视化：它们由不同的人用不同的语言写成，更新节奏从几赫兹到上千赫兹，任何一个模块崩溃或重启都不应该把整机拖死。手工用管道、共享内存或自定义 socket 把这些模块焊在一起，短期可行，长期会卡在三件事上：接口没有契约（改一个字段就要所有模块重编）、时间与坐标没有统一来源（各模块各自换算）、生态无法复用（导航、可视化、仿真、录包都得自己写）。中间件（Middleware）解决的正是“进程之间按什么约定说话”这一层——ROS 2（Robot Operating System 2）就是目前用得最多的中间件之一，名字里的“操作系统”容易误导。[1][5]

它的价值可以拆成四条：

- **进程解耦**：把感知、规划等节点（Node）按需要部署到独立进程，可分别启动和重启，形成故障隔离；
- **语言无关**：C++、Python 节点只要消息定义一致就能互通，算法侧用 Python，实时侧用 C++；
- **生态复用**：导航（Nav2）、坐标变换（TF2）、控制框架（ros2_control）、录包回放（rosbag2）、可视化（RViz 2、Foxglove）和仿真桥都有现成组件，不必重造；
- **分布式**：节点可以跨主机、跨网卡运行，机载计算机和操作台按 Topic 连接，不需要把所有算力都塞进一个盒子。

**ROS 2 由可单独取用的组件和一套共同约定组成。** 各组件的基本分工是：

| 组件 | 负责什么 | 本节位置 |
| --- | --- | --- |
| 通信方式（Topic/Service/Action/Parameter） | 进程之间传数据 | “四种通信方式” |
| TF2 | 坐标变换的单一事实来源 | “TF” |
| ros2_control | 硬件与控制器之间的标准接口 | “ros2_control” |
| rosbag2 与节点日志 | 记录、回放与事后复盘 | “观测与调试” |
| 可视化（RViz 2 / Foxglove） | 空间关系与时间序列检查 | [6.4 节](../06-software-tools-simulation/04-gazebo-rviz2-foxglove.mdx) |
| RMW 与 QoS | 选择底层 DDS 实现与投递策略 | [3.4 节](../03-electrical-embedded/04-real-time-communication-and-buses.mdx) |

TF2、ros2_control 是功能包和框架，rosbag2 与可视化是工具，可以按项目需要组合使用。它们共用消息定义（`.msg`/`.idl`）、命名与命名空间、时间戳语义和坐标命名。

本教程用 ROS 2 组织规划、状态汇总、参数与可视化，用专门设计的实时循环执行高频控制。两部分通过明确的状态与命令接口连接；实时循环可以由 `ros2_control` 或厂商 SDK 实现，具体部署见下文。[4]

> **一句话听懂**：ROS 2 提供组件和通信约定，让感知、规划、控制与工具按统一接口协作。

## 先看全局：一条指令的软件路径

把本节后面所有内容放进一张架构图，一条指令从任务到关节的路径是：

```text
 任务/行为层 → 规划器      ┃  实时域：WBC / 关节控制 → 硬件接口 → SDK/总线 → 驱动器
      ↑           ↑        ┃          ↑                              ↑
    感知系统   状态估计     ┃       状态估计                  状态上报（LowState/JointState）
                          ┃
 规划与编排（普通进程）     ┃ 实时控制循环（ros2_control 或厂商 SDK）
```

图中按运行要求分出普通进程与实时循环：任务和规划产生目标，WBC / 关节控制结合反馈持续更新输出。部署时，要为实时循环配置调度与资源，并测量端到端时序。

后面几节就挂在这条路径上：通信方式决定箭头之间传什么样的数据，TF 决定位姿和时间怎么对齐，ros2_control 对应“硬件接口”那一段，可观测性决定怎么把整条链路录下来复盘；SDK/总线那一段的设备侧细节在 [3.4 节](../03-electrical-embedded/04-real-time-communication-and-buses.mdx)（总线与 DDS）与厂商 SDK（[7]）里。

划边界的三条原则：

1. **状态只有一个估计来源**：姿态、速度的“权威版本”由状态估计模块（[4.4 节](../04-cerebellum-realtime-control/04-state-estimation.mdx)）发布，其他模块消费而不是各自重算；
2. **命令只有一个出口**：同一个命令接口（比如整条腿、或整条手臂）在任一时刻只由一个模块拥有，切换（例如导航接管、遥操作接管、安全降级）必须显式，这正对应 ros2_control 的资源仲裁思想；
3. **时间基准全局一致**：所有消息带时间戳，跨模块的融合和控制按测量时间对齐。

频率分层与 [5.3 节](../05-brain-perception-planning-vla-wam/03-motion-planning.mdx)的表一致：行为层秒级、规划层几十赫兹、控制层百赫兹以上；部署时按各模块的时限分配线程和资源，减少慢任务对高频控制的阻塞。

## 四种通信方式：按数据形态选型

### 节点与四种交互方式

节点（Node）是 ROS 2 里的逻辑计算单元，可以独立运行，也可以与其他节点组合在同一个进程中。节点之间的交互有四种基本形态（ROS 2 文档里叫 Communication Primitives，这里就直说“四种方式”），按数据形态选择交互方式：[1][2]

| 方式 | 形态 | 典型用途 |
| --- | --- | --- |
| Topic | 持续发布/订阅，多对多，无应答 | 关节状态、IMU、点云等流式数据 |
| Service | 一次请求一次应答 | 查询参数、触发标定等短操作 |
| Action | 长任务：目标 + 持续反馈 + 可取消 | 导航到某点、执行一段轨迹 |
| Parameter | 节点自有的可配置值 | 增益、阈值、坐标系名称 |

把持续流数据塞进 Service 会压垮请求方；把需要确认完成的长任务塞进 Topic 会让调用方无法知道成败。Topic 背后的 QoS（Quality of Service，可靠性、历史深度、有效期）属于 DDS 概念，[3.4 节](../03-electrical-embedded/04-real-time-communication-and-buses.mdx)已经介绍过，本节不重讲；这里只补一条 ROS 2 侧的失败模式：QoS 不匹配时，两个节点通常“都能发现彼此、也都在发布”，但数据就是收不到，而且不一定报错。[1]

> **一句话听懂**：选通信方式看数据形态：连续流用 Topic、短问答用 Service、长任务用 Action、配置用 Parameter。

### Launch、生命周期与实时性

*（部署细节：第一遍可跳到[「TF：坐标变换的单一事实来源」](#tf坐标变换的单一事实来源)接着读；节点组合、执行器与实时性留到部署时再查。）*

启动文件（Launch）描述一组节点如何启动、参数如何注入；部分节点还有受管生命周期（Managed Lifecycle）：未配置、未激活、激活、销毁等状态显式转换。它把“系统是否就绪”变成可查询的状态，供后续模块决定何时开始工作。

节点分布在不同进程时，消息通常经 DDS 传输：进程边界带来隔离，也带来序列化和跨进程拷贝的开销。节点组合（Node Composition）允许把多个节点加载进同一个进程、共用同一个执行器（Executor），启用进程内通信后，可减少消息传递中的拷贝；代价是一荣俱荣、一损俱损——一个节点崩溃或阻塞会拖住同进程的其它节点。执行器决定回调在几个线程上、以什么顺序执行：单线程执行器依次运行回调，慢回调会阻塞后续任务；多线程执行器允许并发，需要用互斥或其他同步方式保护共享状态。

高频控制需要明确的周期预算。常见做法是在实时内核与适当调度配置下，用独立线程执行“读取状态 → 更新控制器 → 写入命令”，并预分配内存、控制阻塞操作和数据传输开销。`ros2_control` 的 Controller Manager 就提供这样的更新循环；也可以使用厂商 SDK 的底层循环，由桥接节点交换目标与状态。[4]

部署后，按 [3.5 节](../03-electrical-embedded/05-mcu-realtime-embedded-software.mdx)的方法检查最坏执行时间（Worst-Case Execution Time, WCET）、周期抖动与超时处理。机器人偶发抽动时，分别核对命令通道的拥有者和控制周期记录，定位是指令冲突还是调度问题。

## TF：坐标变换的单一事实来源

TF2（Transform Library 2）维护一棵随时间变化的坐标变换树：广播器（Broadcaster）持续发布变换，监听器（Listener）把变换缓存进缓冲区（Buffer），任何节点都可以查询“过去某一时刻 A 坐标系到 B 坐标系的变换”。[3]

三个高频故障都和时间有关：

- **时间戳不一致**：用 $t = 0$（ROS 约定：0 表示“取最新可用的那一帧”，不是 1970 年）和用消息自带时间戳查询，结果可能完全不同；[4.4 节](../04-cerebellum-realtime-control/04-state-estimation.mdx)“时间不是附属字段”在 TF 查询上同样成立；
- **外推错误**：查询的时刻超出缓存范围（过去太久或未来），通常意味着某一路变换的发布频率不足或时钟不同步；
- **树断裂或成环**：`pelvis` 接错父坐标系、两个节点都声称自己是同一个变换的广播者，模型在 RViz 里就会趴下或散开。

坐标命名和约定遵循 REP-103（单位与右手系）和 REP-105（`map`/`odom`/`base_link` 等标准坐标系）。[6] 对 G1，TF 树通常覆盖 `pelvis`、`torso_link`、各关节 link 和 IMU 固定 link（见 [4.4 节](../04-cerebellum-realtime-control/04-state-estimation.mdx)的模型核对）；关节角到各 link 位姿的正运动学变换由 robot_state_publisher 根据 URDF 和 `JointState` 消息自动完成。

> **一句话听懂**：TF 让各模块查询同一棵带时间的坐标树，回答“在这个时刻，A 相对 B 在哪里、朝向怎样”。

## ros2_control：硬件与控制器之间的标准接口

ros2_control 把“读写硬件”和“控制算法”拆成两层，中间用显式接口连接：[4]

- **Hardware Interface**：每个执行器/传感器声明自己暴露的状态接口（State Interface，如 `position`、`velocity`）和命令接口（Command Interface），由具体的硬件组件（Hardware Component）实现读写；
- **Controller**：控制器只面向接口编程——PID、轨迹控制器不知道也不关心背后是 G1、机械臂还是仿真器；
- **Broadcaster**：一种特殊控制器，只负责把状态接口转成消息发出去，例如 `joint_state_broadcaster`；
- **Controller Manager**：统一管理控制器的加载、激活、切换和硬件资源仲裁——同一时刻一个命令接口只能被一个激活的控制器占用，这从框架层面回答了“谁在发指令”。

资源仲裁是这套架构的核心价值：两个控制器同时写同一个关节，在传统手写代码里是运行时才暴露的隐患，在 ros2_control 里是启动切换时就报错的设计错误。

> **一句话听懂**：ros2_control 把“读写硬件”和“控制算法”拆开、中间用显式接口连接；它的核心价值是资源仲裁——同一时刻一个命令接口只能有一个激活控制器。

## 观测与调试：rosbag2 与日志

架构设计时就要确定记录哪些状态、命令与事件。ROS 2 侧主要靠两件工具：

- **rosbag2**：按 Topic 记录消息，再按时间戳回放分析。排查一次动作偏差时，记录桥接前后的关键量：低层 `rt/lowstate`、桥接后的 `JointState` 与 `Imu`，以及控制器误差。控制器内部变量需要通过专门的数据通道记录；
- **日志**：节点日志应带级别和时间，关键状态切换、命令仲裁结果、QoS 不匹配告警和降级触发必须可回溯（呼应 [3.6 节](../03-electrical-embedded/06-electrical-safety-and-protection.mdx)的故障语义）。日志不要写进实时线程，桥接节点里一次磁盘阻塞就足以打乱控制周期。

空间关系看 RViz 2、时间序列看 Foxglove，两者的分工与用法是 [6.4 节](../06-software-tools-simulation/04-gazebo-rviz2-foxglove.mdx)的整节主题，本节不展开。4.4–[4.6 节](../04-cerebellum-realtime-control/06-balance-and-whole-body-control.mdx)与 [5.3 节](../05-brain-perception-planning-vla-wam/03-motion-planning.mdx)每一节的排查清单，最终都落在这组 bag 记录里“这条曲线长什么样”。
